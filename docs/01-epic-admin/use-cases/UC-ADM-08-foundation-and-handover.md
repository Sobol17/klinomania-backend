## UC-8.1 — Единый источник подписей и цветов статусов

**Актор:** разработчик

**Основной сценарий**
1. Разработчик добавляет или переименовывает статус в enum-классе.
2. Enum реализует `HasLabel` и `HasColor`, поэтому подпись и цвет заданы в одном месте.
3. Все таблицы, формы и фильтры панели подхватывают изменение автоматически.

**Альтернативные и исключительные потоки**
- 3a. До рефакторинга подписи продублированы в трёх местах: приватные `match`
  в `UserResource::roleLabel()` и `CleaningOrderResource::statusLabel()` плюс литералы
  в фильтре статусов. Все три источника подлежат удалению.
- 2a. Добавлен новый статус, но подпись не задана → отображается техническое значение,
  что должно ловиться тестом.

**Постусловия:** подписи статусов не расходятся между разделами панели.

**Критерии приёмки**
- Given подпись статуса изменена в enum, When открыты список и фильтр заказов, Then новая подпись видна в обоих местах.
- Given кодовая база после рефакторинга, When выполнен поиск по `roleLabel` и `statusLabel`, Then совпадений нет.
- Given фильтр статусов заказа, When он открыт, Then его варианты берутся из enum, а не из литералов.

## UC-8.2 — Обработка недопустимых операций и авторизация действий

**Актор:** администратор

**Основной сценарий**
1. Администратор выполняет операцию, недопустимую в текущем состоянии данных.
2. Доменное действие бросает исключение (`InvalidOrderTransition`, `ChecklistIncomplete`).
3. Панель показывает `Notification::danger()` с понятным текстом; данные не изменены.
4. Тот же случай через API по-прежнему возвращает 409 с прежним кодом ошибки.

**Альтернативные и исключительные потоки**
- 3a. До рефакторинга `OrderWorkflow` вызывал `abort(response()->json(...), 409)` —
  в панели это выглядело бы как сырой JSON вместо интерфейса.
- 4a. Контракт API не меняется: `tests/Feature/OrderWorkflowTest.php` остаётся зелёным
  без правки ожиданий — это главный индикатор корректности рефакторинга.
- 2a. Действие, запрещённое политикой (например, изменение `PaymentAttempt`),
  недоступно в интерфейсе и отклоняется при прямом переходе по URL.

**Постусловия:** ошибки бизнес-правил одинаково корректно отображаются в панели и в API.

**Критерии приёмки**
- Given недопустимый переход статуса в панели, When действие выполнено, Then показана нотификация, а не JSON.
- Given тот же переход через API, When запрос выполнен, Then ответ 409 с прежним кодом ошибки.
- Given `OrderWorkflowTest`, When он запущен после рефакторинга, Then он зелёный без изменений ожиданий.
- Given политика запрещает изменение оплаты, When выполнен прямой переход на URL редактирования, Then ответ 403.

## UC-8.3 — Дашборд администратора

**Актор:** администратор

**Основной сценарий**
1. Администратор входит в панель и попадает на дашборд.
2. Видит показатели: заявки по статусам, заявки на сегодня, открытые жалобы,
   сумма подтверждённых оплат за период.
3. Переходит из показателя в соответствующий раздел с уже применённым фильтром.

**Альтернативные потоки**
- 2a. Данных нет → показатели отображают нули, а не ошибку.
- 2b. Стоковые `AccountWidget` и `FilamentInfoWidget` заменены — они не несут
  ценности для заказчика.
- 3a. Навигация сгруппирована: «Продажи», «Каталог», «Пользователи»;
  сейчас все разделы идут плоским списком.

**Критерии приёмки**
- Given администратор вошёл в панель, When открыт дашборд, Then видны заявки по статусам, заявки за сегодня, открытые жалобы и сумма оплат.
- Given пустая база, When открыт дашборд, Then показатели равны нулю и ошибок нет.
- Given нажат показатель «Заявки в обработке», When выполнен переход, Then открыт список заказов с примененным фильтром.

## UC-8.4 — Приёмочный прогон по ТЗ

**Актор:** администратор, заказчик

**Основной сценарий**
1. Команда проходит таблицу трассируемости из [эпика](../00-epic.md) — все 29 буллетов ТЗ.
2. По каждому буллету демонстрируется соответствующий сценарий в развёрнутой панели.
3. Прогоняются `composer test` и `vendor/bin/pint`.
4. Проверяется соответствие `docs/api/openapi.yaml` фактическому поведению API.

**Альтернативные и исключительные потоки**
- 2a. Буллет не воспроизводится → заводится дефект, этап не закрывается.
- 3a. Тесты красные или Pint предлагает правки → этап не закрывается.
- 4a. OpenAPI разошёлся с реализацией → приводится в соответствие;
  это прямое требование `AGENTS.md`.

**Постусловия:** функциональная часть этапа принята.

**Критерии приёмки**
- Given таблица трассируемости, When пройдены все 29 буллетов, Then каждый подтверждён демонстрацией.
- Given `composer test`, When он запущен, Then все тесты зелёные.
- Given `vendor/bin/pint`, When он запущен, Then изменений не предложено.
- Given `docs/api/openapi.yaml`, When он сверен с реализацией, Then расхождений нет.

## UC-8.5 — Передача исходного кода и развёртывание

**Актор:** команда разработки, заказчик

**Основной сценарий**
1. Инструкция по развёртыванию (`docs/deploy.md`, `docs/docker-deploy.md`) дополняется шагами,
   без которых панель работает неполно: `php artisan storage:link` (изображения услуг)
   и запуск воркера очереди (уведомления помечены `ShouldQueue`).
2. Документируется создание администратора: `AdminSeeder`, переменные
   `KLINOMANIA_ADMIN_EMAIL` и `KLINOMANIA_ADMIN_PASSWORD`, обязательная смена
   пароля по умолчанию.
3. Развёртывание воспроизводится с нуля на чистом стенде по инструкции.
4. Заказчик входит в панель по своему логину и паролю через браузер.
5. Исходный код передаётся заказчику.

**Альтернативные и исключительные потоки**
- 1a. Не запущен воркер → письма о новых заказах и жалобах не уходят,
  и на демонстрации это выглядит как несделанная функциональность.
- 1b. Не выполнен `storage:link` → изображения услуг не открываются.
- 2a. Пароль администратора по умолчанию (`password` из `config/klinomania.php`)
  остался на боевом стенде → блокирующий дефект безопасности.
- 3a. Инструкция не воспроизводится → дорабатывается до воспроизводимости.

**Постусловия:** заказчик имеет работающую панель и исходный код.

**Критерии приёмки**
- Given чистый стенд и инструкция, When развёртывание выполнено по шагам, Then панель доступна и вход выполняется.
- Given развёрнутый стенд, When создан новый заказ, Then администратор получает письмо — значит воркер запущен.
- Given развёрнутый стенд, When открыта услуга с изображением, Then изображение отображается.
- Given боевой стенд, When проверен пароль администратора, Then он отличается от значения по умолчанию.
- Given завершение этапа, When выполнена передача, Then заказчик получил исходный код и инструкцию.
