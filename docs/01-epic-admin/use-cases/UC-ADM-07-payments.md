# Use cases — ADM-07. Управление оплатами

Задача: [ADM-07](../tasks/ADM-07-payments.md) · Пункт ТЗ: 1.7

Раздел **только для чтения** — согласованное решение 4 в [эпике](../00-epic.md).
Статусы (`App\Enums\PaymentStatus`, создаётся в этой задаче): `creating` «Создаётся»,
`pending` «Ожидает оплаты», `confirmed` «Оплачено», `failed` «Ошибка».

---

## UC-7.1 — Просмотр списка оплат

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает раздел «Оплаты».
2. Система показывает попытки оплаты: номер заказа со ссылкой, клиент, сумма **в рублях**,
   валюта, провайдер, статус бейджем, дата создания, дата подтверждения.
3. Администратор фильтрует по статусу, провайдеру, периоду создания и подтверждения,
   отдельным фильтром — только ошибочные.
4. Ищет по `external_order_id`, `provider_payment_id` или `public_id` заказа.

**Альтернативные потоки**
- 2a. Оплат нет → пустое состояние.
- 2b. Сумма хранится в копейках (`amount = total_price * 100`) и должна делиться на 100
  при выводе — иначе суммы завышены стократно.
- 2c. `payment_url` — действующая платёжная ссылка, в списке в открытом виде не показывается.

**Критерии приёмки**
- Given есть попытки оплаты, When открыт раздел, Then видны заказ, клиент, сумма, провайдер, статус и даты.
- Given заказ на 5000 ₽, When открыт список оплат, Then сумма отображается как 5 000 ₽, а не 500 000.
- Given применён фильтр «только ошибочные», When он выбран, Then показаны попытки со статусом `failed`.
- Given введён `external_order_id`, When выполнен поиск, Then найдена соответствующая попытка.

## UC-7.2 — Просмотр статуса и карточки оплаты

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает попытку оплаты из списка.
2. Система показывает: заказ, сумма, валюта, провайдер, `external_order_id`,
   `provider_payment_id`, статус, `provider_status`, срок действия ссылки `expires_at`,
   дата создания и `confirmed_at`.
3. Для неуспешных попыток дополнительно показываются `error_code` и `error_message`.

**Альтернативные потоки**
- 2a. Статус `creating` → попытка не дошла до провайдера, `provider_payment_id` пуст.
- 2b. Статус `pending` с истёкшим `expires_at` → визуально помечается как просроченная.
- 3a. Статус `confirmed` → виден `confirmed_at`, а связанный заказ находится в `completed`.

**Критерии приёмки**
- Given открыта карточка оплаты, When страница загружена, Then видны все реквизиты провайдера и статус.
- Given попытка со статусом `failed`, When открыта карточка, Then видны `error_code` и `error_message`.
- Given попытка `pending` с истёкшим сроком, When открыта карточка, Then она помечена как просроченная.

## UC-7.3 — Просмотр привязки оплаты к заказу

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает карточку заказа.
2. В блоке оплат видит все попытки по этому заказу, отсортированные от новых к старым.
3. Видит, какая из попыток подтверждена и покрывает ли сумма стоимость заказа.

**Альтернативные потоки**
- 2a. У заказа несколько попыток: `CreateTBankPayment` переиспользует непросроченную
  попытку в статусе `pending`, поэтому новые создаются только после ошибки или истечения срока.
  Несколько записей — норма, а не дубль платежа.
- 3a. Подтверждённых попыток нет → заказ не оплачен, в блоке это видно явно.

**Критерии приёмки**
- Given у заказа три попытки оплаты, When открыта его карточка, Then показаны все три от новых к старым.
- Given одна из попыток подтверждена, When открыт блок оплат, Then она визуально выделена, а заказ находится в `completed`.
- Given подтверждённых попыток нет, When открыт блок, Then видно, что заказ не оплачен.

**Связанные:** UC-4.8

## UC-7.4 — Переход между оплатой и заказом

**Актор:** администратор

**Основной сценарий**
1. Из списка или карточки оплаты администратор переходит по ссылке на заказ.
2. Открывается карточка заказа со всеми деталями.
3. Из блока оплат заказа он возвращается к конкретной попытке.

**Альтернативные потоки**
- 1a. Заказ удалён → запись оплаты удаляется каскадом
  (`cleaning_order_id` объявлен как `cascadeOnDelete`), поэтому «висячих» оплат не бывает.

**Критерии приёмки**
- Given открыта карточка оплаты, When нажата ссылка на заказ, Then открывается его карточка.
- Given открыта карточка заказа, When в блоке оплат выбрана попытка, Then открывается её карточка.

## UC-7.5 — Запрет ручного изменения записей об оплате

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает раздел оплат.
2. Кнопок создания, редактирования и удаления нет.
3. Попытка открыть URL создания или редактирования напрямую даёт отказ доступа.

**Альтернативные и исключительные потоки**
- 3a. Ограничение опирается на `PaymentAttemptPolicy` из [ADM-08](../tasks/ADM-08-foundation-and-handover.md),
  а не только на скрытие кнопок в интерфейсе.
- 2a. Записи создаются исключительно через `CreateTBankPayment` и обновляются вебхуком
  `TBankNotificationController`; ручная правка рассинхронизировала бы систему с провайдером.
- 2b. Read-only-режим подтверждён заказчиком. Отметка наличной или офлайн-оплаты
  в скоуп эпика не входит; если она понадобится позже — это отдельная задача **ADM-07b**
  со своими правилами подтверждения платежа.

**Постусловия:** данные об оплатах соответствуют данным провайдера.

**Критерии приёмки**
- Given открыт раздел оплат, When он загружен, Then кнопок создания, редактирования и удаления нет.
- Given прямой переход на URL редактирования попытки, When запрос выполнен, Then ответ 403.
- Given попытка изменения через массовое действие, When оно выполняется, Then действие недоступно.
