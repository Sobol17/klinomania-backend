# Use cases — ADM-06. Управление жалобами

Задача: [ADM-06](../tasks/ADM-06-complaints.md) · Пункт ТЗ: 1.6

Домен создаётся с нуля. Статусы (`App\Enums\ComplaintStatus`, создаётся в этой задаче):
`new` «Новая», `in_progress` «В работе», `resolved` «Решена», `rejected` «Отклонена».

---

## UC-6.1 — Подача жалобы клиентом по заказу

**Актор:** клиент (через мобильное приложение)
**Предусловия:** заказ принадлежит клиенту и находится в статусе `in_progress`,
`awaiting_payment` или `completed` — то есть заявка выполняется или уже выполнена.

**Основной сценарий**
1. Клиент вызывает `POST /api/v1/client/orders/{order}/complaints` с темой и текстом.
2. Система проверяет принадлежность заказа, допустимость статуса и валидность полей.
3. `CreateComplaint` создаёт жалобу со статусом `new`, привязанную к заказу и клиенту.
4. Диспатчится `ComplaintCreated`; в ответ возвращается созданная жалоба.

**Альтернативные и исключительные потоки**
- 2a. Заказ принадлежит другому клиенту → 403.
- 2b. Заказ не найден → 404.
- 2c. Заказ в статусе `processing`, `confirmed` или `team_formed` → 409 с кодом
  `complaint_not_allowed`: работа ещё не начата.
- 2e. Заказ в статусе `cancelled` → 409 с тем же кодом: заявка не выполнялась.
- 2d. Не заполнены тема или текст → 422 с описанием полей.
- 1a. Превышена частота подачи → 429.

> **Согласовано с заказчиком:** жалоба доступна только в процессе выполнения заявки
> или после её завершения — статусы `in_progress`, `awaiting_payment`, `completed`.
> Число жалоб по одному заказу не ограничено, ограничена только частота подачи.

**Постусловия:** жалоба сохранена, администраторы уведомлены (UC-6.6).

**Критерии приёмки**
- Given заказ клиента в статусе `in_progress`, When он подаёт жалобу, Then она создана со статусом `new` и привязана к заказу.
- Given заказ клиента в статусе `completed`, When он подаёт жалобу, Then она принимается.
- Given заказ клиента в статусе `confirmed`, When он подаёт жалобу, Then ответ 409 с кодом `complaint_not_allowed` и запись не создана.
- Given заказ клиента в статусе `cancelled`, When он подаёт жалобу, Then ответ 409 и запись не создана.
- Given чужой заказ, When клиент подаёт жалобу, Then ответ 403 и запись не создана.
- Given пустая тема, When жалоба отправлена, Then ответ 422 с указанием поля.
- Given `docs/api/openapi.yaml`, When он открыт, Then эндпоинт описан со всеми кодами ответов.

## UC-6.2 — Просмотр списка жалоб

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает раздел «Жалобы».
2. Система показывает: номер заказа, клиент, тема, статус бейджем, дата подачи, дата решения.
3. Администратор фильтрует по статусу и периоду, ищет по номеру заказа, имени или телефону клиента.
4. Сортирует; по умолчанию — новые сверху.

**Альтернативные потоки**
- 2a. Жалоб нет → пустое состояние.
- 2b. В навигации отображается счётчик жалоб в статусах `new` и `in_progress`.

**Критерии приёмки**
- Given есть жалобы, When открыт раздел, Then видны заказ, клиент, тема, статус и даты.
- Given применён фильтр статуса `new`, When он выбран, Then показаны только новые жалобы.
- Given есть открытые жалобы, When открыта панель, Then в навигации виден их счётчик.

## UC-6.3 — Просмотр жалобы по конкретному заказу

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает карточку заказа.
2. В блоке жалоб видит все жалобы по этому заказу с темами и статусами.
3. Открывает жалобу: тема, полный текст, автор, дата, статус, комментарий администратора,
   кто и когда её закрыл.
4. Из жалобы переходит обратно к заказу и к карточке клиента.

**Альтернативные потоки**
- 2a. Жалоб по заказу нет → блок показывает пустое состояние.
- 3a. Из общего списка жалоб доступен переход к заказу.

**Критерии приёмки**
- Given у заказа есть жалоба, When открыта карточка заказа, Then жалоба видна в соответствующем блоке.
- Given открыта жалоба, When страница загружена, Then видны полный текст, автор, статус и комментарий администратора.
- Given открыта жалоба, When нажата ссылка на заказ, Then открывается карточка этого заказа.

## UC-6.4 — Изменение статуса обработки жалобы

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает жалобу в статусе `new`.
2. Выбирает «Взять в работу»; статус меняется на `in_progress`.
3. После разбора выбирает «Решена» или «Отклонена».
4. Система через `ChangeComplaintStatus` сохраняет статус, `resolved_at` и `resolved_by`.

**Альтернативные и исключительные потоки**
- 3a. При переводе в `resolved` или `rejected` комментарий администратора обязателен (UC-6.5).
- 4a. Повторное изменение статуса закрытой жалобы возможно, но требует подтверждения;
  `resolved_at` и `resolved_by` перезаписываются.
- 2a. Переход сразу из `new` в `resolved` допустим — не каждая жалоба требует разбора.

**Постусловия:** статус актуален, зафиксировано кто и когда закрыл жалобу.

**Критерии приёмки**
- Given жалоба в статусе `new`, When выбрано «Взять в работу», Then статус становится `in_progress`.
- Given жалоба в статусе `in_progress` и заполнен комментарий, When выбрано «Решена», Then статус `resolved`, заполнены `resolved_at` и `resolved_by`.
- Given комментарий не заполнен, When выбрано «Отклонена», Then показана ошибка валидации и статус не изменён.

## UC-6.5 — Комментарий и резолюция администратора

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает жалобу и заполняет `admin_comment` — описание принятого решения.
2. Сохраняет вместе со сменой статуса.
3. Комментарий отображается в карточке жалобы с указанием автора и времени.

**Альтернативные потоки**
- 1a. Комментарий можно заполнить и без смены статуса — как рабочую пометку.
- 3a. Комментарий виден только в панели и клиенту не отправляется —
  информирование клиента о результате разбора в скоуп эпика не входит.

**Критерии приёмки**
- Given открыта жалоба, When заполнен и сохранён комментарий, Then он отображается в карточке.
- Given жалоба закрыта с комментарием, When открыта её карточка, Then видно, кто и когда её закрыл.
- Given заполнен комментарий, When он сохранён, Then клиенту ничего не отправляется.

## UC-6.6 — Уведомление администраторов о новой жалобе

**Актор:** система

**Основной сценарий**
1. Клиент подал жалобу (UC-6.1), диспатчено `ComplaintCreated`.
2. Слушатель `NotifyAdminsAboutNewComplaint` выбирает пользователей с ролью `admin`
   и непустым email.
3. Каждому ставится в очередь `NewComplaintNotification` со ссылкой на жалобу в панели.

**Альтернативные и исключительные потоки**
- 2a. Ни у одного администратора нет email → уведомления не отправляются, жалоба сохранена.
- 3a. Ошибка отправки → повтор по образцу существующего уведомления о новом заказе
  (`tries = 3`, `backoff = [60, 300]`).
- 3b. Не запущен воркер очереди → письма не уходят; шаг проверяется при развёртывании.
- 3c. Клиенту письмо не отправляется.

**Критерии приёмки**
- Given есть администраторы с email, When подана жалоба, Then каждому поставлено уведомление в очередь.
- Given уведомление сформировано, When проверено его содержимое, Then тема содержит номер заказа, а ссылка ведёт на жалобу в панели.
- Given подана жалоба, When проверены получатели, Then клиенту письмо не отправлено.
