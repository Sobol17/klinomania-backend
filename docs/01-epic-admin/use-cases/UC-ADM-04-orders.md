# Use cases — ADM-04. Управление заказами

Задача: [ADM-04](../tasks/ADM-04-orders.md) · Пункт ТЗ: 1.4

Статусы заказа (`App\Enums\OrderStatus`): `processing` «В обработке», `confirmed` «Подтверждена»,
`team_formed` «Команда сформирована», `in_progress` «В работе», `awaiting_payment` «Ожидает оплаты»,
`completed` «Выполнена», `cancelled` «Отменена».

Статусный флоу синхронизирован с актуальным мобильным приложением. Админка не добавляет ручного
«возврата в работу» или других переходов, отсутствующих в мобильном API.

---

## UC-4.1 — Просмотр списка заказов

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает раздел «Заявки».
2. Система показывает заказы: `public_id`, статус бейджем, услуга, телефон клиента,
   назначенные клинеры, сумма, дата и время уборки.
3. Администратор применяет фильтры: статус, услуга, период `scheduled_at`, клинер,
   «без назначенных клинеров».
4. Ищет по `public_id` или телефону клиента.

**Альтернативные потоки**
- 2a. Клинеры не назначены → строка визуально выделяется как требующая внимания.
- 3a. Комбинация фильтров ничего не находит → пустое состояние, фильтры сохраняются.

**Критерии приёмки**
- Given есть заказы, When открыт раздел, Then видны номер, статус бейджем, услуга, клиент, клинеры, сумма и дата.
- Given применён фильтр «без назначенных клинеров», When он выбран, Then показаны только заказы с пустой командой.
- Given введён `public_id`, When выполнен поиск, Then найден ровно один заказ.

## UC-4.2 — Просмотр детальной информации по заказу

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает заказ из списка (маршрут по `public_id`).
2. Система показывает карточку:
   - реквизиты: номер, статус, дата создания, дата и время уборки, комментарий;
   - клиент: имя, телефон, ссылка на карточку пользователя;
   - адрес из `addressSnapshot()`: полный адрес, подъезд, этаж, квартира, домофон, комментарий;
   - состав и суммы из `lineItems` с разбивкой по видам (`base`, `room_option`, `cleaning_option`, `extra_option`);
   - команда клинеров с метками `accepted_at`, `started_at`, `completed_at`;
   - чек-лист (UC-5.1);
   - оплаты (UC-4.8);
   - жалобы по заказу (UC-6.3).
3. Доступны действия смены статуса и работы с командой.

**Альтернативные потоки**
- 2a. Снимок адреса отсутствует → показывается поле `cleaning_orders.address`.
- 2b. Оплат или жалоб нет → соответствующие блоки показывают пустое состояние.

**Критерии приёмки**
- Given открыт заказ, When страница загружена, Then видны клиент, адрес, состав с суммами, команда, чек-лист, оплаты и жалобы.
- Given у заказа есть доп. работы, When открыта карточка, Then они видны отдельными позициями состава.
- Given у заказа нет оплат, When открыта карточка, Then блок оплат показывает пустое состояние без ошибки.

## UC-4.3 — Подтверждение заказа

**Актор:** администратор
**Предусловия:** заказ в статусе `processing`.

**Основной сценарий**
1. Администратор открывает заказ и нажимает «Подтвердить заявку».
2. Система вызывает `OrderWorkflow::confirm()`: блокирует запись, проверяет статус,
   переводит в `confirmed`, диспатчит `OrderStatusChanged`.
3. Показывается нотификация; заказ становится доступен клинерам для принятия.

**Альтернативные и исключительные потоки**
- 1a. Статус не `processing` → кнопка не отображается.
- 2a. Статус изменился между открытием страницы и нажатием → доменное исключение,
  нотификация об ошибке, статус не меняется (страховка от гонки, `lockForUpdate`).

**Постусловия:** заказ в `confirmed`, клиент получил push.

**Критерии приёмки**
- Given заказ в статусе `processing`, When нажато «Подтвердить», Then статус становится `confirmed` и клиент получает push.
- Given заказ в статусе `confirmed`, When открыта карточка, Then кнопка подтверждения отсутствует.
- Given статус изменился параллельно, When нажато «Подтвердить», Then показана нотификация об ошибке, а не сырой JSON.

## UC-4.4 — Отмена заказа администратором

**Актор:** администратор
**Предусловия:** заказ в статусе `processing` или `confirmed`.

**Основной сценарий**
1. Администратор нажимает «Отменить заявку» и подтверждает действие.
2. Система переводит заказ в `cancelled` и диспатчит `OrderStatusChanged`.
3. Клиент получает push об отмене.

**Альтернативные и исключительные потоки**
- 1a. Статус вне `processing` и `confirmed` → действие недоступно; существующий
  `OrderWorkflow::cancel()` запрещает отмену после начала работ.
- 2a. Проверка принадлежности заказа клиенту для администратора не применяется —
  используется отдельный админский путь.
- 2b. На заказ уже назначены клинеры → предупреждение перед подтверждением.

**Критерии приёмки**
- Given заказ в статусе `confirmed`, When администратор его отменяет, Then статус становится `cancelled` и клиент получает push.
- Given заказ в статусе `in_progress`, When открыта карточка, Then действие отмены недоступно.
- Given администратор отменяет чужой заказ, When действие выполнено, Then оно проходит — проверка владельца применяется только к клиенту.

## UC-4.5 — Изменение статуса заказа

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает заказ.
2. Видит только те действия смены статуса, которые допустимы из текущего.
3. Выбирает действие; система выполняет переход через `OrderWorkflow` и диспатчит `OrderStatusChanged`.

**Альтернативные и исключительные потоки**
- 3a. Переход недопустим → доменное исключение мапится в `Notification::danger()`
  с понятным текстом; **сырой JSON пользователю не показывается**.
- 3b. Переход в `completed` минуя оплату не предусмотрен: заказ переводит в `completed`
  только вебхук `TBankNotificationController` при подтверждении оплаты.
- 2a. Поле статуса в форме редактирования недоступно для прямой правки — иначе переход
  обойдёт все проверки `OrderWorkflow`.

**Постусловия:** статус изменён только по допустимому переходу, история согласована.

**Критерии приёмки**
- Given заказ в произвольном статусе, When открыта карточка, Then показаны только допустимые из него действия.
- Given попытка недопустимого перехода, When действие выполнено, Then показана нотификация и статус не изменился.
- Given открыта форма редактирования заказа, When она загружена, Then поле статуса недоступно для прямого изменения.

## UC-4.6 — Назначение клинера на заказ

**Актор:** администратор
**Предусловия:** заказ в статусе `confirmed`; команда не укомплектована.

**Основной сценарий**
1. Администратор нажимает «Назначить клинера».
2. Система показывает клинеров со статусом `active` и `cleaner_profiles.is_active = true`,
   исключая уже назначенных.
3. Администратор выбирает клинера и подтверждает.
4. Система через `AssignCleaner` блокирует заказ, проверяет лимит `service->required_cleaners`
   и отсутствие дубля, добавляет запись в `cleaning_order_cleaners`.
5. Если команда укомплектована — заказ переходит в `team_formed`, а при
   `required_cleaners = 1` сразу в `in_progress`; диспатчится `OrderStatusChanged`.

**Альтернативные и исключительные потоки**
- 4a. Клинер уже в команде → отказ (уникальная пара в пивоте).
- 4b. Команда укомплектована → отказ с указанием требуемого числа клинеров.
- 4c. Клинер заблокирован → он не показан в списке выбора.
- 2a. Подходящих клинеров нет → пустое состояние с пояснением.

**Постусловия:** клинер назначен, заказ виден ему в мобильном приложении.

**Критерии приёмки**
- Given заказ в `confirmed` с `required_cleaners = 2` и одним назначенным, When назначен второй, Then статус становится `team_formed`.
- Given заказ с `required_cleaners = 1`, When назначен клинер, Then статус становится `in_progress`.
- Given команда укомплектована, When назначается ещё один клинер, Then действие отклонено с нотификацией.
- Given клинер уже назначен, When он назначается повторно, Then действие отклонено.
- Given клинер заблокирован, When открыт список выбора, Then он в нём отсутствует.

## UC-4.7 — Снятие клинера с заказа

**Актор:** администратор
**Предусловия:** клинер назначен на заказ и **не начинал работу** — `started_at` в пивоте пуст.

> **Согласовано с заказчиком:** снятие после начала работы запрещено. Клинер, у которого
> проставлен `started_at`, снимается с заказа только через отмену заказа, а не точечным снятием.
> Причина: `started_at` и `completed_at` — основа учёта работы и заработка клинера,
> их удаление задним числом исказило бы отчётность.

**Основной сценарий**
1. Администратор открывает команду заказа и выбирает «Снять» у нужного клинера.
2. Подтверждает действие.
3. Система проверяет, что `started_at` пуст, и удаляет запись из `cleaning_order_cleaners`.
4. Если заказ был в `team_formed`, а команда перестала быть укомплектованной,
   он возвращается в `confirmed` и снова доступен другим клинерам.

**Альтернативные и исключительные потоки**
- 3a. У клинера проставлен `started_at` → действие недоступно; при попытке выполнить его
  напрямую операция отклоняется с понятной нотификацией. Кнопка «Снять» у такой строки не показывается.
- 3b. Заказ в `in_progress`, `awaiting_payment` или `completed` → снятие недоступно:
  в этих статусах работа как минимум начата.
- 3c. Заказ в `team_formed`, но конкретный клинер ещё не начал работу → снятие разрешено.
- 4a. Отметки чек-листа, сделанные снятым клинером, сохраняются: `completed_by`
  объявлен как `nullOnDelete` только для удаления пользователя, а не для снятия с заказа.
- 1a. Нужно освободить заказ от начавшего работу клинера → администратор отменяет заказ (UC-4.4);
  точечного снятия для этого случая нет.

**Постусловия:** отметки времени в пивоте никогда не удаляются задним числом.

**Критерии приёмки**
- Given заказ в `team_formed` с полной командой и пустым `started_at` у клинера, When он снят, Then статус возвращается в `confirmed`.
- Given у клинера проставлен `started_at`, When открыта команда заказа, Then кнопка «Снять» у него отсутствует.
- Given у клинера проставлен `started_at`, When снятие вызвано напрямую, Then операция отклонена и запись пивота цела.
- Given заказ в `completed`, When открыта команда, Then действие снятия недоступно ни для кого.

## UC-4.8 — Просмотр информации об оплате по заказу

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает карточку заказа.
2. В блоке оплат видит все попытки (`payment_attempts`): сумма в рублях, статус,
   провайдер, дата создания, дата подтверждения.
3. Открывает конкретную попытку для просмотра реквизитов провайдера.

**Альтернативные потоки**
- 2a. Попыток нет → пустое состояние.
- 2b. Попытка в статусе `failed` → в строке видны `error_code` и `error_message`.
- 3a. Блок только для чтения — изменение оплат из карточки заказа недоступно.

**Критерии приёмки**
- Given у заказа есть попытки оплаты, When открыта карточка, Then они показаны с суммой в рублях и статусом.
- Given попытка завершилась ошибкой, When открыт блок оплат, Then виден код и текст ошибки.
- Given открыт блок оплат, When он загружен, Then действий создания и редактирования нет.

**Связанные:** UC-7.3

## UC-4.9 — Уведомление клиента при смене статуса администратором

**Актор:** система (следствие действий администратора)

**Основной сценарий**
1. Администратор выполняет любой переход статуса (UC-4.3, UC-4.4, UC-4.5, UC-4.6).
2. `OrderWorkflow` диспатчит `OrderStatusChanged`.
3. Слушатель `SendOrderStatusPush` через `OrderStatusPushService` отправляет push клиенту.

**Альтернативные и исключительные потоки**
- 3a. У клиента нет `fcm_token` или push отключены (`push_notifications_enabled = false`) →
  отправка пропускается, операция администратора не прерывается.
- 3b. Ошибка Firebase → слушатель повторяет попытку (`tries = 3`, `backoff = [60, 300]`);
  администратору ошибка не показывается.
- 3c. Не запущен воркер очереди → уведомление не уходит. Проверка развёртывания.

**Критерии приёмки**
- Given администратор сменил статус, When операция завершена, Then событие `OrderStatusChanged` диспатчено.
- Given у клиента нет `fcm_token`, When статус изменён, Then операция администратора завершается успешно, ошибок нет.
- Given push-сервис недоступен, When статус изменён, Then статус всё равно изменён, а отправка уходит в повтор.
