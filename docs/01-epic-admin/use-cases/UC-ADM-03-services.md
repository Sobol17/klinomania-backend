# Use cases — ADM-03. Управление услугами

Задача: [ADM-03](../tasks/ADM-03-services.md) · Пункт ТЗ: 1.3

---

## UC-3.1 — Просмотр списка услуг

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает раздел «Услуги уборки».
2. Система показывает услуги: превью изображения, название, базовая цена, число опций,
   требуемое число клинеров, статус активности, порядок сортировки.
3. Администратор фильтрует по активности и меняет порядок перетаскиванием.

**Альтернативные потоки**
- 2a. У услуги нет изображения → показывается плейсхолдер.
- 3a. Изменённый порядок сохраняется в `sort_order` и отражается в публичном каталоге.

**Критерии приёмки**
- Given есть услуги, When открыт раздел, Then видны превью, название, цена, число опций и статус.
- Given применён фильтр «только активные», When он выбран, Then услуги с `is_active = false` скрыты.
- Given порядок изменён перетаскиванием, When страница перезагружена, Then новый порядок сохранён.

## UC-3.2 — Создание новой услуги

**Актор:** администратор

**Основной сценарий**
1. Администратор нажимает «Создать».
2. Заполняет секции: основное (название, `slug`, требуемое число клинеров), тексты
   (подзаголовок, краткое и полное описание, подписи о числе клинеров и длительности),
   цены (базовая цена, заработок клинера, цена за м², минимальная цена, валюта),
   параметры площади (`min_area`, `max_area`, `area_step`), изображения.
3. Сохраняет; услуга создаётся, по умолчанию активна.
4. После создания добавляет опции и пункты чек-листа.

**Альтернативные и исключительные потоки**
- 2a. `slug` уже занят → ошибка валидации (в БД поле `unique`).
- 2b. `min_area` больше `max_area` → ошибка валидации.
- 3a. Услуга без опций и чек-листа сохраняется, но помечена как незавершённая в списке.

**Критерии приёмки**
- Given заполнены обязательные поля, When услуга сохранена, Then она создана и видна в списке.
- Given `slug` дублирует существующий, When форма отправлена, Then показана ошибка и запись не создана.
- Given `min_area > max_area`, When форма отправлена, Then показана ошибка валидации.

## UC-3.3 — Редактирование услуги: стоимость и описание

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает услугу на редактирование.
2. Меняет стоимость, тексты описаний или параметры площади.
3. Сохраняет; изменения немедленно отражаются в публичном API
   `GET /api/v1/client/services/{id}`.

**Альтернативные потоки**
- 2a. Изменение цены **не затрагивает уже созданные заказы** — их состав зафиксирован
  в `order_line_items` и `service_snapshot`. Интерфейс сообщает об этом.
- 3a. Изменён `cleaner_base_earnings` → влияет только на новые заказы.

**Критерии приёмки**
- Given изменена базовая цена, When изменения сохранены, Then публичный API отдаёт новую цену.
- Given изменена цена, When открыт ранее созданный заказ, Then его сумма и состав не изменились.
- Given изменены тексты описаний, When они сохранены, Then они видны в публичном API.

## UC-3.4 — Удаление услуги

**Актор:** администратор

**Основной сценарий**
1. Администратор выбирает «Удалить» и подтверждает действие.
2. Система проверяет наличие связанных заказов.
3. Заказов нет → услуга удаляется вместе с опциями и пунктами чек-листа (каскад).

**Альтернативные и исключительные потоки**
- 3a. Связанные заказы есть → удаление отклоняется с объяснением
  (`cleaning_orders.cleaning_service_id` объявлен как `restrictOnDelete`); предлагается
  деактивировать услугу вместо удаления. Пользователь **не** должен увидеть ошибку СУБД.
- 3b. Услуга участвует в активном заказе → отдельное предупреждение.

**Постусловия:** каталог не содержит удалённую услугу; исторические заказы целы.

**Критерии приёмки**
- Given услуга без заказов, When она удалена, Then запись и её опции удалены.
- Given услуга со связанным заказом, When нажато «Удалить», Then показана понятная нотификация, а не ошибка СУБД, и запись цела.
- Given удаление отклонено, When открыт список услуг, Then услуга на месте и доступна для деактивации.

**Связанные:** UC-3.7

## UC-3.5 — Загрузка изображений услуги

**Актор:** администратор
**Статус требования:** подтверждено заказчиком — загрузка выполняется из панели,
вставка внешней ссылки как единственный способ не допускается.

**Основной сценарий**
1. Администратор открывает секцию изображений в карточке услуги.
2. Загружает главное изображение — оно сохраняется на диск `public`,
   в `cleaning_services.image_url` записывается полный URL.
3. Загружает изображения галереи; они сохраняются массивом в `cleaning_services.gallery` (json).
4. Меняет порядок изображений галереи перетаскиванием.

**Альтернативные и исключительные потоки**
- 2a. В поле уже лежит внешний CDN-адрес → он отображается как есть и не требует
  перезагрузки файла при сохранении формы (см. допущение 1 эпика).
- 2b. Недопустимый тип файла или превышен размер → ошибка валидации.
- 2c. Отсутствует симлинк `public/storage` → изображение не открывается;
  шаг `php artisan storage:link` обязателен в инструкции по развёртыванию.

**Критерии приёмки**
- Given загружен файл главного изображения, When услуга сохранена, Then файл лежит на диске `public`, а в `image_url` записан полный URL.
- Given у услуги внешний CDN-адрес, When форма открыта и сохранена без изменений, Then адрес не изменился.
- Given загружены изображения галереи, When порядок изменён и сохранён, Then публичный API отдаёт их в новом порядке.

## UC-3.6 — Управление опциями услуги

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает карточку услуги и переходит к опциям.
2. Видит вкладки по группам: «Количество комнат» (`room`), «Тип уборки» (`cleaning`),
   «Дополнительные работы» (`extra`).
3. Добавляет опцию: `code`, `title`, `subtitle`, надбавка `price_modifier`,
   доля клинера `cleaner_revenue_percent`, зона чек-листа `checklist_zone`,
   флаги `is_addon`, `is_default`, `is_active`, порядок.
4. Сохраняет; опция доступна при оформлении заказа.

**Альтернативные и исключительные потоки**
- 3a. `code` уже занят в пределах услуги → ошибка (в БД уникальная пара
  `[cleaning_service_id, code]`).
- 3b. Настройка совместимости опций через `service_option_dependencies`.
- 4a. Деактивированная опция исчезает из формы заказа, но остаётся в существующих заказах.

**Критерии приёмки**
- Given открыта карточка услуги, When выбрана вкладка группы, Then показаны опции только этой группы.
- Given добавлена опция группы `extra`, When создаётся новый заказ, Then опция доступна для выбора.
- Given `code` дублируется внутри услуги, When форма сохранена, Then показана ошибка и запись не создана.
- Given опция деактивирована, When открыта форма нового заказа, Then опция недоступна, а прежние заказы не изменились.

## UC-3.7 — Включение и отключение услуги в каталоге

**Актор:** администратор

**Основной сценарий**
1. Администратор переключает `is_active` в списке или в карточке.
2. Система сохраняет значение.
3. Неактивная услуга исчезает из публичного каталога `GET /api/v1/client/services`.

**Альтернативные потоки**
- 3a. Существующие заказы по этой услуге продолжают обрабатываться нормально.
- 1a. Деактивация — рекомендуемая альтернатива удалению при наличии заказов (UC-3.4).

**Критерии приёмки**
- Given активная услуга, When она деактивирована, Then публичный каталог её не возвращает.
- Given деактивированная услуга, When открыт существующий заказ по ней, Then заказ отображается и обрабатывается нормально.
- Given деактивированная услуга, When она снова активирована, Then она возвращается в каталог.
