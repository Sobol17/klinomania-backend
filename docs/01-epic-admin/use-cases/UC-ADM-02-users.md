# Use cases — ADM-02. Управление пользователями

Задача: [ADM-02](../tasks/ADM-02-users.md) · Пункт ТЗ: 1.2

---

## UC-2.1 — Просмотр списка клиентов

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает раздел «Пользователи».
2. Выбирает вкладку «Клиенты».
3. Система показывает пользователей с `role = client`: имя, телефон, email, статус, дата регистрации.
4. Администратор ищет по имени, телефону или email и фильтрует по статусу.

**Альтернативные потоки**
- 3a. Клиентов нет → пустое состояние с пояснением.
- 4a. Поиск ничего не нашёл → сообщение об отсутствии результатов, фильтры сохраняются.

**Критерии приёмки**
- Given есть клиенты и клинеры, When открыта вкладка «Клиенты», Then показаны только `role = client`.
- Given введён фрагмент телефона, When выполнен поиск, Then список сужается до совпадений.
- Given выбран фильтр статуса `blocked`, When он применён, Then показаны только заблокированные.

## UC-2.2 — Просмотр списка клинеров

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает вкладку «Клинеры».
2. Система показывает пользователей с `role = cleaner`, включая статус и признак рабочей
   доступности `cleaner_profiles.is_active`.
3. Администратор фильтрует по статусу и доступности.

**Альтернативные потоки**
- 2a. У клинера нет профиля `CleanerProfile` → строка помечена как требующая внимания,
  интерфейс не падает.

**Критерии приёмки**
- Given есть клинеры, When открыта вкладка «Клинеры», Then показаны только `role = cleaner`.
- Given у клинера отсутствует профиль, When открыт список, Then строка отображается без ошибки.
- Given применён фильтр доступности, When он выбран, Then список сужается корректно.

## UC-2.3 — Создание учётной записи пользователя

**Актор:** администратор

**Основной сценарий**
1. Администратор нажимает «Создать» в разделе пользователей.
2. Выбирает роль — клиент или клинер.
3. Форма показывает блок профиля, соответствующий роли.
4. Заполняет имя, телефон, email, при необходимости пароль и поля профиля.
5. Сохраняет; система создаёт `User` и связанный `ClientProfile` или `CleanerProfile`,
   статус по умолчанию — `active`.

**Альтернативные и исключительные потоки**
- 4a. Телефон или email уже заняты → ошибка валидации по конкретному полю, данные формы сохранены.
- 2a. Выбрана роль клинера → генерируется код доступа, его хэш пишется в `cleaner_profiles.access_code_hash`,
  код показывается администратору один раз.
- 5a. Ошибка при создании профиля → транзакция откатывается, «осиротевший» `User` не создаётся.

**Постусловия:** учётная запись создана вместе с профилем и может использоваться в мобильном приложении.

**Критерии приёмки**
- Given заполненная форма с ролью «клиент», When она сохранена, Then созданы `User` и `ClientProfile`.
- Given телефон уже занят, When форма отправлена, Then показана ошибка и запись не создана.
- Given роль «клинер», When запись сохранена, Then код доступа показан один раз, а в БД лежит его хэш.

**Связанные:** UC-2.10

## UC-2.4 — Редактирование учётной записи

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает пользователя на редактирование.
2. Меняет реквизиты или поля профиля.
3. Сохраняет; изменения записываются в `users` и в таблицу профиля.

**Альтернативные потоки**
- 2a. Поле пароля оставлено пустым → пароль не меняется (текущее поведение `UserResource`:
  `->dehydrated(fn (?string $state): bool => filled($state))`).
- 2b. Пароль заполнен → сохраняется в хэшированном виде за счёт каста `'password' => 'hashed'`.
- 2c. Смена роли существующего пользователя → предупреждение о влиянии на доступ и профиль.
- 3a. Новый телефон или email заняты → ошибка валидации, изменения не применены.

**Критерии приёмки**
- Given открытая форма редактирования, When пароль оставлен пустым и форма сохранена, Then прежний пароль продолжает работать.
- Given введён новый пароль, When форма сохранена, Then вход выполняется новым паролем, а в БД хранится хэш.
- Given изменён телефон на занятый, When форма отправлена, Then показана ошибка и данные не изменены.

## UC-2.5 — Просмотр карточки пользователя

**Актор:** администратор

**Основной сценарий**
1. Администратор выбирает пользователя в списке и открывает карточку.
2. Система показывает реквизиты, роль, статус, дату регистрации, поля профиля.
3. Ниже — история заказов: для клиента по связи `CleaningOrder::client()`,
   для клинера — по `User::cleaningOrders()` через пивот `cleaning_order_cleaners`.
4. Из карточки доступны действия: редактировать, заблокировать или разблокировать.

**Альтернативные потоки**
- 3a. Заказов нет → пустое состояние.
- 3b. Клинер: у каждого заказа видны метки `accepted_at`, `started_at`, `completed_at` из пивота.

**Критерии приёмки**
- Given открыта карточка клиента, When страница загружена, Then видны реквизиты, профиль, статус и его заказы.
- Given открыта карточка клинера, When страница загружена, Then видны заказы из пивота с временными метками.
- Given у пользователя нет заказов, When открыта карточка, Then показано пустое состояние без ошибки.

## UC-2.6 — Изменение статуса пользователя

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает карточку или строку списка.
2. Меняет статус между `active` и `blocked`.
3. Система сохраняет `users.status`, проставляет или снимает `blocked_at` и показывает нотификацию.

**Альтернативные потоки**
- 2a. Пользователь — клинер: `users.status` определяет доступ в систему, а
  `cleaner_profiles.is_active` — рабочую доступность для назначения на заказы.
  Это разные вещи, интерфейс объясняет разницу.
- 3a. Администратор пытается заблокировать сам себя → операция запрещена.

**Постусловия:** статус актуален; при переводе в `blocked` выполняются шаги UC-2.7.

**Критерии приёмки**
- Given активный пользователь, When статус изменён на `blocked`, Then `users.status = blocked` и заполнен `blocked_at`.
- Given администратор редактирует свою запись, When он пытается себя заблокировать, Then операция отклонена.
- Given клинер заблокирован, When открыт его профиль, Then видно, что `is_active` и статус — разные признаки.

**Связанные:** UC-2.7, UC-2.8, UC-1.5

## UC-2.7 — Блокировка пользователя

**Актор:** администратор

**Основной сценарий**
1. Администратор выбирает «Заблокировать» и подтверждает действие.
2. Система через `BlockUser` в транзакции: ставит `status = blocked`, заполняет `blocked_at`
   и **удаляет все токены Sanctum** пользователя.
3. Показывается нотификация об успехе.

**Альтернативные и исключительные потоки**
- 2a. У пользователя есть активные заказы в работе → предупреждение перед подтверждением;
  заказы блокировкой не отменяются.
- 2b. Ошибка на любом шаге → транзакция откатывается целиком, частичной блокировки не бывает.

**Постусловия:** ранее выданные токены недействительны, вход невозможен.

**Критерии приёмки**
- Given у клиента есть действующий токен Sanctum, When он заблокирован, Then запрос с этим токеном возвращает 401.
- Given заблокированный пользователь, When открыта его карточка, Then виден статус и дата блокировки.
- Given у пользователя есть заказ в статусе `in_progress`, When выполняется блокировка, Then показано предупреждение, а заказ не отменяется.

**Связанные:** UC-2.9

## UC-2.8 — Восстановление доступа пользователя

**Актор:** администратор

**Основной сценарий**
1. Администратор открывает заблокированного пользователя и выбирает «Разблокировать».
2. Система через `UnblockUser` ставит `status = active` и обнуляет `blocked_at`.
3. Показывается нотификация.

**Альтернативные потоки**
- 2a. Токены не восстанавливаются — пользователь проходит вход заново.
  Для клинера может потребоваться сброс кода доступа (UC-2.10).

**Постусловия:** пользователь снова может авторизоваться.

**Критерии приёмки**
- Given заблокированный клиент, When он разблокирован, Then `status = active`, `blocked_at` пуст и OTP-вход снова проходит.
- Given пользователь разблокирован, When он выполняет вход, Then ему выдаётся новый токен.

## UC-2.9 — Отказ заблокированному пользователю в доступе к API

**Актор:** заблокированный клиент или клинер

**Основной сценарий**
1. Пользователь пытается войти через мобильное приложение.
2. Клиент проходит `ClientAuthController::verifyCode()`, клинер — `CleanerAuthController::login()`.
3. Учётные данные верны, но статус — `blocked`.
4. Система отвечает 403 с кодом `user_blocked` и токен не выдаёт.

**Альтернативные потоки**
- 1a. У пользователя остался старый токен → он уже удалён при блокировке (UC-2.7), ответ 401.

**Постусловия:** заблокированный пользователь не работает с API ни по новому, ни по старому токену.

**Критерии приёмки**
- Given заблокированный клиент с верным кодом OTP, When он вызывает `verify-code`, Then ответ 403 с кодом `user_blocked` и токена нет.
- Given заблокированный клинер с верным кодом доступа, When он вызывает `login`, Then ответ 403 и токена нет.
- Given `docs/api/openapi.yaml`, When он открыт, Then новый код ответа описан на обоих эндпоинтах.

## UC-2.10 — Сброс кода доступа клинера

**Актор:** администратор
**Предусловия:** у пользователя роль `cleaner` и есть `CleanerProfile`.

**Основной сценарий**
1. Администратор открывает карточку клинера и выбирает «Сбросить код доступа».
2. Система генерирует новый код, записывает его хэш в `cleaner_profiles.access_code_hash`.
3. Код показывается администратору **один раз** для передачи клинеру.

**Альтернативные потоки**
- 3a. Администратор закрыл окно, не сохранив код → повторный показ невозможен, нужен новый сброс.
- 2a. У пользователя нет профиля клинера → действие недоступно.

**Постусловия:** прежний код недействителен.

**Критерии приёмки**
- Given клинер с рабочим кодом доступа, When код сброшен, Then вход по старому коду отклоняется, а по новому проходит.
- Given код показан, When страница перезагружена, Then код повторно не отображается.
- Given пользователь с ролью `client`, When открыта его карточка, Then действие сброса кода недоступно.
