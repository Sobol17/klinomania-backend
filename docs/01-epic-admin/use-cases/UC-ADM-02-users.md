# Use cases — ADM-02. Управление пользователями

Задача: [ADM-02](../tasks/ADM-02-users.md) · Пункт ТЗ: 1.2

Актор всех действующих сценариев — администратор.
Баны и блокировки исключены заказчиком как отсутствующие в ТЗ.

## UC-2.1 — Просмотр клиентов

Администратор открывает «Пользователи» и выбирает вкладку «Клиент».
Список содержит только клиентов; доступны поиск по имени, телефону и email и фильтр роли.
При отсутствии совпадений показывается пустая таблица.

## UC-2.2 — Просмотр клинеров

Вкладка «Клинер» содержит только клинеров. Видны реквизиты и существующий признак
активности профиля; можно выбрать активных или неактивных клинеров фильтром.
Отсутствие профиля не приводит к ошибке страницы.

## UC-2.3 — Создание пользователя

Администратор выбирает роль и заполняет реквизиты и появившийся блок профиля.
Для клиента доступны имя, адрес и настройки уведомлений; для клинера — имя и активность.
User и профиль сохраняются в одной транзакции. Занятые телефон/email дают ошибку поля.
При создании клинера генерируется шестизначный код: хэш сохраняется в профиле,
код показывается уведомлением для передачи клинеру. Повторно прочитать его из карточки нельзя.

## UC-2.4 — Редактирование пользователя

Реквизиты и профиль сохраняются вместе. Пустой пароль сохраняет прежний хэш;
введённый пароль хэшируется. При смене роли форма предупреждает об изменении доступа:
прежний профиль сохраняется, профиль выбранной роли создаётся при необходимости.
После смены роли на клинера код можно выдать действием сброса.

## UC-2.5 — Карточка пользователя

Из списка открывается карточка с реквизитами, ролью, датой регистрации и профилем.
История клиента содержит только заказы с его `client_id`, клинера — назначенные ему
через `cleaning_order_cleaners`. Заказ можно открыть; при отсутствии заказов таблица пуста.
Доступны редактирование и, при наличии профиля клинера, сброс кода.

## UC-2.6 — Статус пользователя

Исключён из объёма: статус пользователя не вводится.
Существующий `cleaner_profiles.is_active` редактируется в профиле. Текущий API
не разрешает вход неактивному клинеру; эта семантика не меняется.

## UC-2.7 — Блокировка пользователя

Исключён из объёма по решению заказчика.

## UC-2.8 — Разблокировка пользователя

Исключён из объёма по решению заказчика.

## UC-2.9 — Отказ заблокированному пользователю

Исключён из объёма по решению заказчика. API-контракт не меняется.

## UC-2.10 — Сброс кода клинера

Администратор открывает карточку или редактирование клинера с профилем и подтверждает
сброс. Генерируется новый шестизначный код, отличный от прежнего; сохраняется только хэш.
Код показывается однократным уведомлением, которое можно закрыть после передачи.
Если код потерян, нужен новый сброс. Активность клинера не меняется.
Для клиентов, администраторов и клинеров без профиля действие недоступно.
При отключённой тестовой заглушке старый код отклоняется, новый позволяет войти активному
клинеру. При включённой заглушке действует код из конфигурации, о чём предупреждает диалог.
