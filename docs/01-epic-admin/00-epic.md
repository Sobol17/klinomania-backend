# EP-ADM — Административная панель Klinomania (Filament)

**Тип:** эпик
**Статус:** к разработке
**Пункты ТЗ:** 1.1–1.7, 2
**Дата составления:** 2026-08-30

---

## 1. Цель

Довести административную панель на `/admin` до полного покрытия ТЗ: авторизация администратора,
разделы управления пользователями, услугами, заказами, чек-листами, жалобами и оплатами,
интеграция с существующим бизнес-слоем `app/Modules/*` и передача исходного кода заказчику.

## 2. Бизнес-ценность

Сегодня операционная работа (подтверждение заявок, назначение клинеров, разбор жалоб, сверка оплат)
делается вручную через БД или не делается вовсе. Панель переводит эти операции в интерфейс,
доступный по логину и паролю через браузер, и закрывает этап приёмки перед заказчиком.

## 3. Границы эпика

**Входит:**
- веб-панель Filament и все семь разделов ТЗ;
- минимально необходимые изменения бэкенда: статус/блокировка пользователя, домен жалоб (БД + API + админка),
  enum-классы статусов, admin-методы workflow заказа;
- тесты Pest на новую функциональность;
- документация по развёртыванию и передача кода.

**Не входит:**
- мобильные приложения клиента и клинера;
- редизайн публичного API помимо новых эндпоинтов жалоб и проверки блокировки;
- биллинг, взаиморасчёты с клинерами, выгрузки в бухгалтерию;
- мультиязычность панели (остаётся русский, см. допущение 3).

Названия в ТЗ и в кодовой базе расходятся. Во всех задачах используются имена из кода.

| Термин ТЗ | Сущность в коде | Таблица |

| Чек-лист (шаблон) | `App\Models\ServiceChecklistItem`, зона `App\Enums\ChecklistZone` | `service_checklist_items` |

## 6. Архитектурный принцип

**Панель переиспользует бизнес-слой, а не дублирует его.** Прецедент уже заложен в коде: страницы
Filament вызывают действия из `app/Modules/*/Actions`. Любая новая операция админки (назначение клинера,
смена статуса жалобы, отметка пункта чек-листа) реализуется как действие в модуле и вызывается из панели —
не как бизнес-логика внутри Filament-ресурса. Это гарантирует одинаковое поведение админки и мобильного API.

Следствие: изменения API, вызванные этим эпиком, требуют обновления `docs/api/openapi.yaml`
**в том же коммите** (требование `AGENTS.md`).

## 9. Согласованные решения

Зафиксировано заказчиком, пересмотру в рамках эпика не подлежит.

1. **Назначение клинера администратором обязательно.** Существующий `OrderWorkflow::accept()` —
   операция самого клинера, для админки её недостаточно. Реализуется отдельным действием
   `AssignCleaner` в [ADM-04](tasks/ADM-04-orders.md), см. UC-4.6 и UC-4.7.
2. **Загрузка изображений услуг из панели обязательна.** Администратор загружает файл
   главного изображения и галереи прямо в карточке услуги, а не вставляет внешнюю ссылку.
   Реализуется в [ADM-03](tasks/ADM-03-services.md), см. UC-3.5.
3. **Жалоба допустима только во время выполнения заявки или после её завершения.**
   Разрешённые статусы заказа: `in_progress`, `awaiting_payment`, `completed`.
   Запрещено в `processing`, `confirmed`, `team_formed` (работа ещё не начата)
   и в `cancelled` (заявка не выполнялась). Реализуется в [ADM-06](tasks/ADM-06-complaints.md), см. UC-6.1.
4. **Оплаты — только чтение.** Ручное создание, редактирование и удаление `payment_attempts`
   из панели не предусмотрены. Записи создаются `CreateTBankPayment` и обновляются вебхуком
   `TBankNotificationController`; ручная правка рассинхронизировала бы систему с провайдером.
   Реализуется в [ADM-07](tasks/ADM-07-payments.md), см. UC-7.5.

## 10. Открытые допущения

1. **Хранение изображений.** Файлы грузятся на диск `public`, но в
   `cleaning_services.image_url` и `.gallery` записывается **полный URL**, а не путь к файлу.
   Причина: `ClientServiceController` отдаёт значение колонки как есть, и переход на пути
   сломал бы контракт публичного API. Требуется `php artisan storage:link` на всех окружениях.
   Существующие записи с внешними CDN-адресами продолжают работать без миграции данных.
2. **Число жалоб по одному заказу не ограничено**, ограничена только частота подачи.
   Отдельного правила «одна жалоба на заказ» заказчик не заявлял.
3. **Локализация.** Каталога `lang/` нет, все подписи — инлайн-строки на русском. Сохраняем текущую
   конвенцию. Вынос в `lang/ru/*.php` — отдельная необязательная задача, в оценку не входит.
4. **Оценки** — в story points по Фибоначчи. Если нужны часы, потребуется переразметка.
5. **Роль администратора одна.** Разделения на суперадмина, менеджера и оператора ТЗ не требует;
   политики в ADM-08 проектируются с расчётом, что такое разделение может появиться позже.

## 11. Риски

| Риск | Влияние | Митигация |
|---|---|---|
| `OrderWorkflow` завершает недопустимые переходы через `abort(response()->json(...), 409)` — в панели это выдаст сырой JSON вместо нотификации | Высокое, блокирует ADM-04 и ADM-05 | Рефакторинг на доменные исключения в ADM-08; контроллеры мапят их в 409, панель — в `Notification::danger()` |
| В `OrderWorkflow` нет админского назначения клинера, `accept()` инициируется самим клинером | Высокое, ТЗ 1.4 не закрывается | Новое действие `AssignCleaner` с теми же гарантиями блокировки и лимита команды (ADM-04) |
| Домен жалоб пишется с нуля вместе с API — влияет на мобильные приложения | Среднее | Контракт эндпоинтов согласовать до реализации, `openapi.yaml` обновить в том же коммите |
| Блокировка пользователя не отзывает выданные Sanctum-токены — заблокированный клиент продолжит работать до истечения токена | Высокое | Отзыв токенов в том же действии + проверка статуса в аутентификации (UC-2.7, UC-2.9) |
| Два независимых типа пунктов чек-листа (`OrderChecklistItem` и `OrderExtraChecklistItem`) легко упустить | Среднее | Явно зафиксировано в ADM-05; тест на заказ с доп. работами |
| `cleaning_services` защищена `restrictOnDelete` от `cleaning_orders` — прямое удаление услуги упадёт | Среднее | UC-3.4: удаление только при отсутствии заказов, иначе деактивация |
| Изображения услуг сейчас внешние URL; переключение на загрузку меняет выдачу публичного API | Среднее | Допущение 2: хранить полный URL, контракт не менять |
