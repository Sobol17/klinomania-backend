## Цель

Подготовить общий каркас, на который опираются остальные задачи, и закрыть требования
к результату этапа: работающая панель, интеграция с бэкендом, передача исходного кода.

Задача **сознательно разорвана во времени**: каркас блокирует ADM-02, ADM-04, ADM-06, ADM-07
и делается первым; приёмка и передача — последними.

## Часть A — каркас (выполняется первой)

### A1. Enum-классы как единый источник подписей

Сейчас подписи статусов продублированы приватными методами `match` внутри ресурсов:
`UserResource::roleLabel()` и `CleaningOrderResource::statusLabel()`; в фильтре статусов
`CleaningOrderResource` те же строки записаны **в третий раз** литералами.

- [ ] `App\Enums\UserRole`, `OrderStatus` — реализовать `Filament\Support\Contracts\HasLabel`
      и `HasColor`; `ChecklistZone` уже имеет `label()`, привести к тому же контракту.
- [ ] Создаваемые в эпике `UserStatus` ([ADM-02](ADM-02-users.md)), `ComplaintStatus`
      ([ADM-06](ADM-06-complaints.md)), `PaymentStatus` ([ADM-07](ADM-07-payments.md)) —
      сразу с этими контрактами.
- [ ] Удалить приватные `roleLabel()` и `statusLabel()`, перевести фильтры на `::class` enum.

### A2. Доменные исключения вместо `abort()`

`OrderWorkflow` завершает недопустимые переходы через `abort(response()->json(...), 409)` —
HTTP-связанность, из-за которой панель получит сырой JSON вместо нотификации.
Подробности в [ADM-04](ADM-04-orders.md).

- [ ] `app/Modules/Orders/Exceptions/InvalidOrderTransition.php`, `ChecklistIncomplete.php`.
- [ ] `OrderWorkflow` бросает исключения; контроллеры API мапят их в прежние 409 с кодами
      `invalid_order_transition` и `checklist_incomplete` — **контракт API не меняется**.
- [ ] Базовое действие Filament, превращающее эти исключения в `Notification::danger()`.

### A3. Политики доступа

Каталога `app/Policies` не существует, `Gate::define` нигде не вызывается: единственная
авторизация — `User::canAccessPanel()`. Для одной роли этого достаточно, но ТЗ требует
«интеграции с backend-частью» и разделения ответственности.

- [ ] Политики для `User`, `CleaningService`, `CleaningOrder`, `Complaint`, `PaymentAttempt`.
- [ ] `PaymentAttemptPolicy` запрещает `create`, `update`, `delete` — техническая опора
      read-only-режима из ADM-07.
- [ ] Политики спроектировать так, чтобы добавление ролей менеджера или оператора не требовало
      переписывания ресурсов.

### A4. Оформление панели

- [ ] `->brandName('Клиномания')`, логотип, favicon в `AdminPanelProvider`.
- [ ] Группы навигации: «Продажи» (заявки, оплаты, жалобы), «Каталог» (услуги, доп. услуги),
      «Пользователи»; сейчас все ресурсы лежат плоским списком.
- [ ] Глобальный поиск по номеру заказа, телефону и email клиента.
- [ ] Дашборд: заявки по статусам, заявки за сегодня, открытые жалобы, сумма подтверждённых
      оплат за период. Стоковые `AccountWidget` и `FilamentInfoWidget` заменить.

## Критерии приёмки

1. Подписи и цвета статусов задаются в одном месте — enum-классах; дублирующих `match`
   в ресурсах не осталось.
2. Недопустимый переход статуса в панели показывает нотификацию; тот же случай в API
   по-прежнему даёт 409 с прежним кодом ошибки.
3. Политики зарегистрированы, `PaymentAttempt` защищён от изменения.
4. Навигация сгруппирована, панель оформлена под заказчика, работает глобальный поиск.
5. Дашборд показывает заявки по статусам, заявки за сегодня, открытые жалобы и сумму оплат.
6. `composer test` зелёный, `vendor/bin/pint` чистый.
7. Все 29 буллетов ТЗ подтверждены на демо.
8. Инструкция по развёртыванию воспроизводится с нуля на чистом стенде.
9. Исходный код передан заказчику.

## Риски

- Рефакторинг `OrderWorkflow` идёт по живому коду, который используют и клиентский,
  и клинерский API. Единственная страховка — существующий `OrderWorkflowTest`,
  его нельзя переписывать под новое поведение.
- Пароль администратора по умолчанию (`password` в `config/klinomania.php`) не должен уехать
  на прод. Проверка обязательна перед сдачей.
- Уведомления помечены `ShouldQueue`: без запущенного воркера письма не уходят,
  а на демонстрации это выглядит как несделанная функциональность.
