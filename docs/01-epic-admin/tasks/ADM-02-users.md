## Согласованный объём

Блокировки и баны исключены по решению заказчика: в ТЗ такого функционала нет.
`users.status`, `blocked_at`, `UserStatus`, блокировка/разблокировка, отзыв токенов
и ошибка `user_blocked` не добавляются. Публичный API не изменяется, поэтому правки OpenAPI не требуются.

## Реализовано

- [x] Вкладки всех пользователей, клиентов, клинеров и администраторов; фильтр роли.
- [x] Поиск по имени, телефону и email.
- [x] Колонка и фильтр существующего признака активности клинера.
- [x] Создание и редактирование пользователя вместе с профилем выбранной роли в транзакции.
- [x] Профиль клиента: имя, адрес, push-уведомления, email-рассылка.
- [x] Профиль клинера: имя и существующий флаг `is_active`.
- [x] При смене роли сохраняются прежний профиль и история; создаётся профиль новой роли.
- [x] Пустой пароль при редактировании сохраняет прежний хэш.
- [x] Карточка пользователя: реквизиты, роль, профиль, дата регистрации.
- [x] История заказов клиента по `client_id`, клинера — через `cleaning_order_cleaners`.
- [x] При создании клинера генерируется код; в БД сохраняется только хэш.
- [x] Сброс кода из карточки и редактирования с подтверждением и однократным уведомлением.
- [x] Сброс не меняет `is_active`; новый код отличается от прежнего.

## Особенности

`cleaner_profiles.is_active` — существующий признак: текущий API отклоняет вход
неактивного клинера. Это поведение сохранено, отдельная система банов не вводится.
При включённом `klinomania.auth.cleaner_code_stub_enabled` вход использует тестовый
код конфигурации; персональные коды работают при отключённой заглушке.
Смена роли на клинера позволяет выдать код отдельным действием после сохранения.
